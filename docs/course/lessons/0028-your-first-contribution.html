Your first contribution

Completion is not remembering 28 pages. It is taking one real problem from evidence to a reviewable, tested change without losing the system boundary.

⏱ 15 min + your task🎯 Produce one contribution packet a reviewer can trust
Course graduation test: another engineer can read your packet and answer what broke, where it broke, why the fix belongs there, and what proves it—without trusting your intuition.

Choose a first task with a short blast radius

Good first tasks have a reproducible behavior, an existing owner and a nearby test pattern: a translation, validation, missing UI state, incorrect route payload, or focused integration bug. Avoid beginning with a new retry system, schema redesign, PBX migration or cross-repository protocol change.

If your task is outside VoIP, use the same lesson: locate the narrow addon, read its manifest and neighbors, trace its ORM/UI boundary, and reuse its test style. The platform skills from Lessons 1–10 travel with you.

Build the contribution packet

ArtifactWhat to record
ReproductionExact branch/SHA, database/module state, action, observed result, expected result.
Ownership mapRepository, addon, model/component, external boundary, and callers of the function you will change.
InvariantOne plain sentence that must stay true—for example, “a redelivered cost event cannot create a second remote charge.”
Failing proofThe narrowest existing test layer that fails before the fix and passes after it.
Minimal changeFix the shared root cause. Do not add recovery machinery for a failure you did not reproduce.
VerificationTargeted test, relevant module suite, lint/static check, and manual/shared-staging proof only when the behavior requires it.
HandoffBefore/after behavior, commands and results, skipped checks, remaining risk, screenshots only when they prove UI behavior.

Use the right repository proof

Community / Enterprise

Python model/controller tests; Hoot for JS units; tours for browser journeys; module install/update proof. Include upgrade work when stored schema or data meaning changes.

IAP Phone Service

Controller/model tests with every Telnyx, Wazo and IAP call mocked explicitly. Money/security paths need stable-key and ownership assertions.

VoIP infrastructure

Run the repository's mise run test config harness. Real signaling/audio still needs the documented integration check.

Integration addons

Prove the integration behavior plus the inherited core behavior you rely on. Do not duplicate core logic in CRM, Helpdesk or Sales.

Review yourself before asking others

  1. Read the diff, not just the final files. Remove unrelated formatting and speculative helpers.
  2. Check access rights, record rules, sudo(), public routes, tokens and resource ownership.
  3. Check retries against side effects: database uniqueness is not remote idempotency.
  4. Check translations, batch recordsets, query count, browser cleanup and failure messages.
  5. Rerun the targeted test after any rebase or branch switch; report skipped proof honestly.
Branch discipline: confirm the team's current target before editing. Do not publish, push, open a PR or touch shared services merely because the code is ready; those are separate authorized actions.

Your graduation checklist

Capstone prompt

Give your agent a real small issue and say: “Teach while pairing. First reproduce read-only and make me name the owner and invariant. Then help me add the smallest failing test, implement the root-cause fix, run the proportional checks, and draft a factual handoff. Stop before any remote action.”

Your teacher is an agent—interrupt it. Before you change code, ask it to challenge your ownership map and invariant. If either answer is vague, keep tracing together until you can point to the exact boundary.
