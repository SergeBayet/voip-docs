Shipping an Odoo change

A contribution is not the diff. It is a claim about behavior, backed by a focused test and placed on the correct version line.

⏱ 12 min🎯 Prepare a reviewable, upgrade-safe change

Fix, feature or migration?

  • Bug fix: establish the regression and target the oldest maintained version where the bug exists, following team policy; later lines are typically forward-ported.
  • Feature: target master unless the owning team explicitly decides otherwise.
  • Stored data/schema change: ask how existing databases reach the new shape. An install test on an empty database is not an upgrade proof.
  • Cross-repository API change: identify deployment order and backward compatibility before either side merges.

What a reviewer needs

Why

One concrete before/after story, not a tour of every edited line.

Scope

The owner module and why sibling callers remain correct.

Proof

Exact automated tests plus any unavoidable manual check.

Risk

Security, money, data migration, concurrency and external contracts.

Review standard: separate “I can imagine a problem” from “I would ask the author to change this before merge.” Reproduce or trace a concrete path before calling something blocking.
Practice outside VoIP

Pick a small recent change in any addon. From its manifest and tests, infer the owning team, affected branch family, upgrade risk and minimum verification. This skill transfers across Odoo.
