Doorbells & robots

How news travels between machines that all fail sometimes — with one durable owner at each handoff.

⏱ ~12 minutes🎯 Goal: choose the correct ack, dedup and recovery contract🧩 Builds on: Lessons 7, 16, 18
Start with registered mail. 🏠 An HTTP 2xx means “the next owner accepted responsibility,” not necessarily “all downstream work finished.” Telnyx and Wazo keep a letter when the shop answers 503. The shop tries the database. The database verifies the signed token, persists the event once, answers 200, then processes it after the response. Durable acceptance is the handoff point.

The event geography — every doorbell on the street

Read the picture left to right. The carrier and PBX push news to the shop. Telnyx names are translated only where needed (call.cost → call_cost; number and requirement events get stable underscored names). Wazo call names stay call_created, call_answered, call_updated and call_ended after normalization and leg filtering. Everything reaches one database route: /voip/api/phone_service/event.

Three doors, three locks — and why each

Each hop uses a different signature scheme. That's not inconsistency — each lock fits its door:§14

DoorLockWhy this lock, here
Telnyx → shopEd25519 signature over timestamp|body, ±300 s tolerancePublic internet. The carrier publishes one public key; anyone can verify, nobody can forge, and the timestamp window kills replay attacks.
Wazo → shopPer-tenant secret in the body, constant-time compareAn intra-infrastructure hop over TLS. The secret (minted at tenant provisioning) both authenticates the sender and identifies which tenant is talking.
Shop → your DBPurpose-scoped, expiring signed token over the complete envelopeThe token is signed with that client's stored client_secret_hash; Enterprise derives the same verifier from its local secret. No separate body can drift from the signature.
The rule behind the token. Public identity such as client_uuid cannot authenticate a callback. The verifier must derive from the secret, be scoped to phone_service_webhook, expire quickly, and cover the whole envelope.

The fourth arrow — your DB calling the shop (sync_queue, buy_number…) — is an ordinary API call authenticated with client_uuid + client_secret. Keep request authentication and callback-token verification distinct.

"Did I already get this letter?" — dedup is a constraint, not an if

Refusing to sign means the sender rings again — so every event can arrive twice, and your handler must treat a replay as a no-op. Parrot's answer is mechanical and identical at every hop:

  • Deterministic ids. The shop names Wazo events event_id = call_id:event_name — a fact has one name, so its redelivery collides with its first delivery. A random UUID per delivery would make every replay look new.
  • A UNIQUE constraint where facts are stored: the shop's cost webhook event, Enterprise voip.phone.service.event, cost lines and voicemail messages. Payments reserve one row per (client, reference_type, reference_id).
  • Race-safe insert. A cheap pre-check may avoid the common duplicate, but the unique index inside a savepoint handles concurrent delivery. Two workers can race; exactly one creates the fact.
Every dedup is a constraint, not an if. An if seen: return check has a race window between the check and the write. A database UNIQUE index has none — the database itself is the referee. If you catch yourself writing a "have I processed this?" flag, reach for a constraint instead.§15

When you can't finish: refuse to sign

Say a call.cost reaches the shop before its lifecycle correlation identifies a client. The shop answers 503 and stores nothing; Telnyx redelivers later. Once the client is known, the shop forwards, stores the event once and reserves the payment. If database delivery fails, it still returns 503 so Telnyx redelivers; the stored event/payment keys prevent a second charge while the callback gets another chance.

Ack only after ownership transfers. Before persistence, an unexplained 200 can destroy the sender's retry. After Enterprise has durably registered a unique event, answering 200 before slower processing is deliberate: the database now owns the work. Find the durability boundary before judging the status code.

Recovery is flow-specific. Number status has a slow poll as well as push; webhook URL synchronization has a one-off retry; PBX provisioning and payments have explicit state machines. Live call events do not all have a polling reconstruction. Add recovery only when the source and business consequence justify it.

The robots — who heals what

Some multi-step paths need scheduled reconciliation. The six most instructive are:§15

SideRobotEveryWhat it heals
🏪submit ordering1 minauthorize credits + send number orders to Telnyx
🏪resume PBX provisioning5 minlay the next tenant brick; mark failed after 2 h stuck
🏪recover payments10 minretry charges on exponential backoff (30 min·2ⁿ, cap 1 day; ≥5 tries ⇒ delinquent)
🏪reconcile client state1 mindrive Telnyx routing to match the disabled intent
🏠heal provisioning30 minre-drive under-provisioned active DIDs against the checklist
🏠link orphan cost lines30 minre-match cost lines that arrived before their call record

Notice what makes robots safe: steps converge when repeated, and “only once” facts use constraints. A robot that re-runs finished work must change nothing. That does not imply every webhook needs a robot.

⚠️ The cautionary tale — the quarantine that got reverted. Once, an unattributable call.cost event looked like it deserved real machinery: the team built a quarantine model + retry cron + escalation email for events that couldn't find their client. It worked. It was also reverted as over-engineered: three new moving parts, each needing observability and maintenance, to handle a rare case for which the upstream already had a retry queue. The fix that survived is one line of behavior: answer 503 and let Telnyx redeliver. The team's philosophy, verbatim from its engineering notes: fix what is broken; do not harden what merely could break — and when a failure is silent, the cheap reusable fix is logging the reason well, not building infrastructure around it. Before you add a table, a cron, or an alert: who already holds this letter?
