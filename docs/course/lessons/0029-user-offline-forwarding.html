When the user is not connected

Understand why one small product rule crosses Odoo, Phone Service, Wazo configuration, Asterisk routing and event reporting.

⏱ 20 min🎯 Review the offline-forwarding feature without guessing🧩 Zero PBX knowledge assumed
The durable idea: confd writes the switchboard's instructions; Asterisk follows them during the live call; events tell Odoo what happened afterward. A routing success is not automatically a call-history success.

First, the school-office story

Imagine a school office trying to reach a teacher. The teacher can have several classroom phones. The office keeps a card saying: “try every classroom phone; if none is connected, call this mobile number.”

What “connected” means

A browser says “I can receive calls here” by sending a SIP REGISTER. A registered device becomes a contact on the user's PJSIP AOR—the user's phone address book entry inside Asterisk.

  • One open registered tab means at least one contact is available.
  • Several tabs may mean several contacts, but it is still one user.
  • “Offline” for this rule means all applicable contacts are unavailable. It is not a green-dot presence status.
  • Closing a tab may leave its contact visible until its registration expires.

The old behavior: wait and wake the browser

A disconnected browser might come back after receiving a push notification. Wazo's dial_mobile path therefore keeps the call alive while a notification tries to wake the device.

The wakeup token is like a note saying: “do not give up immediately; this user has an app that may wake up.” With that token present, “no current contact” does not immediately use the ordinary Fail Destination.

The new product rule

Contacts nowValid backup numberExpected call behavior
At least oneYes or noRing the available SIP/browser contacts normally.
NoneYesAsterisk gets CHANUNAVAIL and immediately calls the Fail Destination.
NoneNoKeep the old dial_mobile push-wakeup behavior.
Why remove the token only when a backup exists? Removing it allows immediate failure routing. Removing it when no backup exists would throw away the only mechanism that can wake a disconnected browser.

Why this crosses Enterprise and IAP

Enterprise owns the employee/user fields and therefore knows the intended backup number. It normalizes the value to E.164 form and prefers mobile_phone, then phone.

Enterprise must not receive Wazo's master credential. It asks Phone Service for the outcome “update this user's routing.” Phone Service validates the request, scopes it to the customer's Wazo tenant, calls Confd to store fail_destination, and calls Wazo Auth to revoke or restore the wakeup token.

Where the committed application work lives
  • enterprise/voip/models/res_users.py — choose valid mobile_phone, then phone.
  • enterprise/voip/models/res_users_settings.py — send the Fail Destination or restore wakeup behavior.
  • iap_services/phone_service/controllers/pbx_controller.py — accept only an external outcall as a Fail Destination.
  • iap_services/phone_service/models/phone_service_pbx_tenant_ops.py — update Wazo fallbacks and revoke the wakeup token after the route is stored.

Confd versus SSH

Confd API: change one user's data

“For user 42, use this mobile number as the Fail Destination.” This is normal application behavior and is performed by Phone Service over HTTPS.

SSH: change the server's rulebook

“Whenever any offline Fail Destination is used, stamp the outgoing channel with this correlation header.” That custom dialplan file lives on the Wazo machine.

SSH means Secure Shell: an encrypted remote terminal into another computer. It is the maintenance door, not part of a customer's call. We need it for the experiment because the custom Asterisk dialplan file belongs to the Wazo server filesystem, not to a user record managed by Confd.

Do not confuse SSH with your development tunnel

ConnectionDirectionWhy it exists
Enterprise on 8870 → IAP on 8470Local application requestYour customer database asks your local Phone Service to change routing.

The tunnel does not grant shell access to Wazo, and SSH does not deliver Wazo events to your local IAP. A full test needs both directions working.

SSH has a larger blast radius. A file under the Wazo server can affect every tenant hosted there. It requires privileged access, can break routing if its syntax is wrong, may disappear when a lab is rebuilt, and exposes sensitive logs. That is why the experiment belongs on Wazo 02, uses one guarded file, has a rollback, and must later become managed infrastructure or a Wazo plugin.

Why the conversation header is needed

One human call creates several technical channels: caller → Wazo, Wazo → browser, or Wazo → external mobile. Each channel can have its own SIP Call-ID. Asterisk's linkedid is the family name tying those channels together, and Wazo exposes it as conversation_id.

The old dial_mobile path stamped X-Odoo-Conversation-Id while waking the browser. Immediate Fail Destination routing bypasses that path, so a Wazo pre-dial handler must stamp the external outgoing PJSIP channel instead.

[xivo-subrfwd-extension]
exten = s,1,NoOp(Odoo offline Fail Destination)
same  =   n,GotoIf($["${WAZO_FWD_TYPE}" != "USER_CHANUNAVAIL"]?return)
same  =   n,GoSub(wazo-add-pre-dial-hook,s,1(odoo-set-conversation-id-header))
same  =   n(return),Return()

[odoo-set-conversation-id-header]
exten = s,1,Set(PJSIP_HEADER(add,X-Odoo-Conversation-Id)=${CHANNEL(linkedid)})
same  =   n,Return()

The guard means “do this only because the user's devices were unavailable.” The pre-dial handler means “run on the newly created external channel.” No new identifier is generated.

The Wazo 02 experiment, with reasons

  1. Check the Wazo version. The hook order above was verified against 26.07; another version may have different contexts.
  2. Search for an existing hook. Two owners defining the same xivo-subrfwd-extension priority would conflict.
  3. Add one file under /etc/asterisk/extensions_extra.d/. This is Wazo's supported custom-dialplan directory; do not edit package-generated dialplan files.
  4. Run dialplan reload. This reloads routing instructions without rebooting the whole server.
  5. Test three states. Online contact, offline with valid backup, and offline without valid backup.
  6. Follow one ID. Compare Asterisk linkedid, the outbound header, Wazo event conversation_id, the IAP webhook and Odoo records.
  7. Roll back the one file. Restore the user's original token/fallback using the Odoo synchronization path.

The unfinished proof

The external telephone ringing proves the switchboard route. It does not prove that the Odoo call log is correct.

When dial_mobile is bypassed, there may be no user softphone leg and no enriched push event. We still need a real Wazo 02 trace—or the private plugin contract—to show which event carries both the target user and the shared conversation ID into Odoo. Without that evidence, the product may forward the call correctly while creating only technical conversation/leg records and no user-facing voip.call.

Two acceptance gates: Gate 1 is “the correct external phone rings immediately.” Gate 2 is “Odoo receives enough correctly correlated events to create exactly the intended call history.” Never report Gate 2 from Gate 1 evidence.

Your review checklist

  1. Does the state matrix above hold for all three cases?
  2. Is only valid normalized mobile_phone, then phone, used?
  3. Is the fallback stored before the wakeup token is revoked?
  4. Is the existing wakeup behavior restored when no valid backup exists?
  5. Is the Wazo hook restricted to USER_CHANUNAVAIL?
  6. Does an online contact avoid the external Fail Destination?
  7. Does one linkedid survive the SIP header, Wazo event, IAP webhook and Odoo records?
  8. Do multiple tabs and redelivered events still result in one visible notification and one intended call record?
  9. Is the direct Wazo file treated as a lab experiment until a durable deployment owner is agreed?
