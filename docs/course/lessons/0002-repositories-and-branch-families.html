Repositories and branch families

Think of the checkout as a campus: each repository owns a different kind of change, but compatible branches must walk together.

⏱ 10 min🎯 Choose the correct repository and baseline

The repositories you will touch

master/odoo

Core framework, web client, mail, IAP client and community addons. A generic framework fix belongs here.

master/enterprise

Enterprise addons. The shipped VoIP product and its integrations live here.

master/iap-apps

The hosted phone_service broker. Its shared Phone Service foundation and provisioning policy are released independently from the customer database; verify the target branch and deployment separately.

upgrade

Version-to-version data/schema migrations. Renaming a stored field may require work here.

voip-infra

Versioned Kamailio edge configuration and its tests. It forwards signaling; it does not carry audio.

voip-docs

Architecture, operator material and the byte-identical course twin.

Branch families, in plain words

master is the next Odoo version. Stable branches (for example 19.0) accept appropriate fixes, not new features. Community and Enterprise must use compatible version branches. A service repository can ship independently, so verify its deployed branch and API contract instead of assuming the same branch name.

Current teaching anchor: the source walkthrough uses stable Enterprise, Community, IAP Phone Service and voip-infra paths. The shared voip-common, phone-service-common, voip-boi and scheduled-call work are treated as integrated architecture. Re-check the actual branches, commits and deployment target before making a release or merge claim.

A lazy placement test

Ask: “Who must own this behavior if every consumer disappeared?” A generic ORM capability stays in odoo; a VoIP customer feature stays in Enterprise; carrier credentials and multi-database brokerage stay in phone_service; version migration logic stays in upgrade.
