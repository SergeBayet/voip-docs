Security & trust boundaries

Every request carries a claim about who sent it. Authentication proves the claim; authorization limits what that identity may do.

⏱ 12 min🎯 Review an Odoo path from attacker to record

The server-side layers

  • Route authentication decides whether the caller is public, a user, bearer-authenticated, and so on.
  • ACLs grant create/read/write/delete at model level.
  • Record rules filter which records an operation may touch.
  • Field groups and model checks protect sensitive fields and domain-specific actions.
  • Validation treats IDs, JSON, filenames, amounts and external payloads as hostile until checked.
sudo() is a trust-boundary crossing. It is sometimes necessary for a signed webhook or system job, but it removes normal ACL and record-rule protection. Resolve and verify ownership before elevating, minimize the elevated block, and never use it to silence an unexplained access error.

A real public webhook

phone_service_api_controller.py accepts a public POST because no user session exists. It first requires a signed, scoped, expiring token derived from the database's client secret; rejects malformed envelopes; allowlists event types; validates required fields; then persists the event once. Only that validated event is processed with elevated access.

Security review drill

Read master/enterprise/voip/controllers/phone_service_api_controller.py beside models/phone_service_event.py. Identify authentication, input validation, idempotency, authorization/elevation and the HTTP acknowledgement boundary.
