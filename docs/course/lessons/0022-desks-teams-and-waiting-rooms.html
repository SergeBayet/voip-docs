Desks, teams & waiting rooms

An external number gets a destination; an internal extension gets a short code; a queue turns eligible users into live PBX agents.

⏱ 11 min🎯 Change a route without writing to derived state🧩 Builds on Lessons 19 and 21
The useful distinction: a DID is the public street address; an extension is a room number inside the building. Both route to typed Odoo records, but neither is the other.

DIDs route directly

voip.did.number.destination_ref is the writable routing link. It is an Odoo Reference field whose allow-list comes from PBX_DESTINATION_MODELS: user, extension, group, queue, IVR, Call Flow, sound, contact, or mailbox. The PBX service converts the selected record to Wazo routing data.

did.user_id is not the general route. It is a stored convenience field computed only when the destination is directly a res.users record. That is why the “one DID per user” constraint applies to direct user assignment, while a main number can still route to a group or flow.

Extensions are internal short codes

voip.extension accepts 3–5 digits, cannot start with zero, and is globally unique. Its destination_ref can point to a user, group, or queue. User extensions also own the user's PBX identity: Wazo user, line, SIP credentials, and personal mailbox are provisioned through that path.

Deletion crosses a transaction boundary. Deleting a user extension clears local SIP credentials immediately, then schedules the PBX extension deletion and user deprovisioning only after the database transaction commits. A rollback therefore does not delete a live PBX identity for a change Odoo discarded.

Provisioning heals toward a level

The 30-minute heal cron does not blindly repeat every step. _filter_under_provisioned() selects live, directly user-assigned DIDs that are missing concrete pieces: SIP credentials, Wazo user/line ids, a routing extension, or—once active—the inbound route ids. A transient failure also requests a run about a minute later.

This is a reusable reliability pattern: define “complete,” inspect the current level, and re-drive only incomplete records.

Queues: author eligibility, derive runtime rows

What an admin writes

  • allowed_user_ids
  • allowed_call_group_ids
  • strategy, timeouts, capacity, music, fallbacks

What sync derives

  • resolved_agent_user_ids
  • one voip.queue.agent per resolved user
  • Wazo agent ids, membership, status and sequence

_get_resolved_agent_users() unions the direct users with the users of allowed groups and removes portal/share users. Sync creates any missing user extensions, creates or adopts one Wazo agent per user, materializes the queue-agent rows, and reconciles Wazo membership. The sequence follows the resolved extension order; the two source Many2many fields are not a user-authored priority list.

Agents can join and leave their assigned queues now. The queue form and softphone call action_join_queue/action_leave_queue or set_current_user_queue_membership. Status is pulled from Wazo after membership changes and on explicit refresh; it is not a scheduled status cron.
