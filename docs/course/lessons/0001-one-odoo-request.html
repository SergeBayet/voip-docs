One Odoo request, end to end

Odoo is a city: the browser asks at the front desk, the model applies the rules, and PostgreSQL keeps the records.

⏱ 10 min🎯 Put each responsibility in the right layer
The practical rule: controllers translate transport; models own business rules; the ORM owns persistence and access checks. A UI is another caller, not the source of truth.

The five objects to recognize

ThingJobTypical clue
Route/controllerParse the request, authenticate, return a transport response.@http.route
EnvironmentCarry the database cursor, current user, context and superuser state.request.env or self.env
ModelName data and enforce business behavior for every caller.models.Model
RecordsetRepresent zero, one or many records and provide model methods.self, browse(), search()
TransactionCommit the whole request on success; roll it back on failure.Usually invisible—do not call commit() in normal model code.

Put the invariant below the UI

If a DID may only belong to its own database, the check cannot live only in a wizard. Imports, RPC calls and tests would bypass it. Put the rule in the model/service boundary used by every caller; let the wizard explain the error.
