Anatomy of an addon

An addon is a small vertical slice: Python behavior, declared data, browser code, permissions and tests packed behind one manifest.

⏱ 10 min🎯 Navigate an unfamiliar Odoo module

Read an addon in this order

  1. __manifest__.py: purpose, dependencies, loaded files, assets and install behavior.
  2. models: data ownership and invariants.
  3. security: who may access which records.
  4. views/data: UI, actions, menus, scheduled jobs and seed records.
  5. static/src: Owl components, services, patches and browser assets.
  6. tests: the most executable statement of intended behavior.
Read the real module

Open master/enterprise/voip/__manifest__.py. Its depends list tells you which framework concepts are prerequisites; its asset bundles tell you where softphone code enters the web client. Then inspect models/__init__.py and tests/__init__.py.

Dependencies are architecture

When addon B declares a dependency on addon A, B may extend A's models and load after it. Avoid adding a dependency merely to import one convenience: it increases installation coupling for every database. Integration addons such as voip_crm keep CRM-specific behavior out of the core voip addon.
