Debugging across the stack

A VoIP symptom is not a component. Name the failed connection, follow one stable identifier, and stop at the first broken handoff.

⏱ 12 min🎯 Turn a vague report into one owned boundary🧩 Uses the whole course
Say this before touching code: “The failure is between X and Y, on protocol Z, after identifier K was created.” If you cannot fill that sentence, collect evidence first.

Follow one identifier, not every log

Number purchase

Start with E.164 number → Enterprise DID → shop number/order → Telnyx order/sub-order → requirement group. State which ledger stopped advancing.

Call event

Start with event id plus conversation/SIP call ids → shop forward → Enterprise event → call and leg records. Do not merge Telnyx call_control_id with Wazo ids.

Charge

Start with Telnyx event id → payment (reference_type, reference_id) → remote key → Enterprise cost line.

Provisioning

Start with client_uuid → tenant → named PBX op → returned Wazo ids → mirrored Enterprise fields.

Fast symptom decisions

  • Number stays pending: separate order progress from callback delivery. Check shop state before changing the Enterprise widget.
  • Browser will not register: inspect WSS/SIP status. An edge 503, an unknown SIP user, and bad browser credentials are different failures.
  • Call rings but has no audio: signaling already worked. Inspect media negotiation, device permission, ICE/NAT and RTP path; the IAP shop is not in the audio lane.
  • Duplicate-looking record: identify the missing stable key before adding a search or retry. Check the existing unique indexes first.
  • Only CRM/helpdesk behavior is wrong: begin in the narrow integration addon, not core voip.

Reproduce at the cheapest layer

Use a pure model test for ORM/state logic, Hoot for a frontend unit, a tour only for a real browser journey, and shared staging only when the question requires a real edge, Wazo, Telnyx or inbound webhook. Python and browser tests mock external systems; a successful mock proves your code contract, not carrier health.

Shared staging is evidence, not a scratchpad. Use a disposable database, record the exact client/number/event you created, avoid destructive probes, and never print credentials. Follow parrot-local-testing-guide.md for the current tunnel and endpoint contract.
