Leaving a message

Wazo stores the audio. Odoo stores the business record. Phone Service carries metadata one way and fetches the recording the other way.

⏱ 10 min🎯 Trace a voicemail from fallback to play button🧩 Builds on Lessons 20 and 22
Two copies, two jobs. Wazo is the telephony source for the mailbox and audio. Odoo's voip.voicemail and voip.voicemail.message make them searchable, playable, emailable, secured business records.

Personal and shared mailboxes

Every provisioned Phone user gets one personal mailbox automatically. It becomes the default no-answer destination and cannot be deleted independently. A database may also have one shared mailbox for a team. Mailbox numbers default to 90<record id>; *98 reaches the current user's mailbox.

A mailbox may use a voip.sound as its unavailable greeting. Sync creates or updates the Wazo mailbox and then uploads or removes that greeting. Lesson 26 follows text-to-speech sound generation.

The event keeps its real name

Wazo webhookd sends either global_voicemail_message_created or user_voicemail_message_created to Phone Service. The shop preserves that event name; Enterprise handles both with the same message consumer. The shop-to-database request is not an HMAC header: the complete envelope is inside a short-lived, scoped token signed with that client's secret hash.

Enterprise first inserts one voip.phone.service.event row under a unique event_id, returns 200, and processes after the HTTP response closes. This keeps Wazo's webhook request short. Database concurrency errors get a small bounded retry; other failures are logged and surfaced to the affected user.

Exactly once at two levels

KeyHole it closes
voip.phone.service.event(event_id)The same broker event arriving repeatedly.
voip.voicemail.message(event_id)The same message event being consumed twice.
(voicemail_id, pbx_message_id)The same PBX recording arriving under another event name or id.

The consumer searches first for the common duplicate, then relies on unique indexes for races. A unique collision becomes ConcurrencyError, which the outer event processor retries with a fresh transaction.

Push metadata, pull audio

The event contains caller, duration, folder, mailbox and message ids—not the binary. For a non-empty message, Enterprise calls get_voicemail_message_recording through Phone Service and stores the returned bytes as an attachment. The list view streams that attachment through /voip/voicemail/message/<id>; a configured mailbox email receives it once.

Debugging boundary: a recording-download failure logs a warning and leaves the message row without audio. The current code has no recording-fetch cron or retry button. A later distinct event for the same PBX message can try again, but ordinary replay of an already-acknowledged top-level event is deduplicated. Do not promise automatic healing that is not implemented.
Trace it in code
  • voip/models/voip_voicemail.py — personal/shared lifecycle and greeting sync.
  • voip/models/phone_service_event.py — persist, acknowledge, dispatch both event names.
  • voip/models/voip_voicemail_message.py — two-key dedupe, recording pull and email.
  • phone_service/utils/wazo_events.py + utils/webhook.py — Wazo forwarding and signed envelope.
